# 테마 설계 — 머지 게임 (정식 앱, 이름 미정)

> `apps/proto_merge` 승격 후 정식 앱의 **레벨디자인/컨텐츠 설계** 문서.
> PRD(`docs/prd/<이름>.md`)보다 앞선다: 여기서 테마와 체인을 확정한 뒤
> 그 위에서 이름·수익모델·성공지표를 정해 PRD를 쓴다.
> 앱 이름이 정해지면 이 문서는 `docs/design/<이름>-themes.md`로 옮긴다.
>
> - **문서 상태**: 초안 (2026-09-27), §7 결정 5개 확정 (2026-11-05)
> - **검증된 전제**: 드래그드롭 머지 조작 (`docs/prd/proto_merge.md` 판정 기록)
> - 각 결정에 상태를 표기한다: **[확정]** / **[제안 — 확인 필요]**

---

## 1. 구조 용어 **[확정]**

컨텐츠가 4층으로 쌓인다. 층을 섞어 부르면 설계가 엉키므로 용어를 고정한다.

| 층 | 뜻 | 예 |
|---|---|---|
| **테마** | 해금 단위. 컨텐츠의 뼈대 | 동굴이 있는 숲 |
| **지대** | 테마 안의 구역. 보드 위 칸이 어느 지대인지 갖는다 | 숲 / 동굴 |
| **체인** | 머지 계보 하나. **생성기 1개 = 체인 1개** | 나무 체인, 돌 체인 |
| **레벨** | 체인 안의 단계 | 씨앗(1) … 거목(5) |

**자원**은 이 4층 밖이다. 보드 칸을 차지하지 않고 **창고**에 쌓이며, 테마를 넘어
이동한다. 보드 위 조각(아이템·생성기)과 창고 자원은 다른 종류의 것이다.

## 2. 주 진행축 — 보드 확장 **[제안 — 확인 필요]**

**작게 시작해 자원으로 보드를 넓힌다.** 이것이 이 게임의 목표 구조다.

프로토타입에 없던 "왜 계속 머지하는가"의 답이 여기서 나온다. 그리고 루프가
스스로 물린다:

```
좁은 보드 → 체인을 굴려 최고 레벨 달성 → 그 자리가 자원 산출원으로 굳는다
   ↑                                              ↓
보드 확장 ←──────────── 자원 축적 ←───────── 칸이 모자라진다
```

핵심은 **최고 레벨 조각이 보드에 영구히 남아 자원을 산출한다**는 점이다(§4).
산출원이 늘수록 보드가 좁아지므로, 확장은 보상이 아니라 **필요**가 된다.
공간 압박이 곧 동기다.

## 3. 첫 테마 — 동굴이 있는 숲 **[제안 — 확인 필요]**

지대 2개를 한 테마에 넣어, 확장에 **방향**을 준다.

```
        ┌───────────────┐
  숲    │  가로 확장 →  │   지상. 나무 체인.
        ├───────────────┤
  동굴  │  아래 확장 ↓  │   지하. 돌 체인.
        └───────────────┘
```

- **가로로 넓히면** 숲이 커진다 — 나무를 더 심는다.
- **아래로 파면** 동굴이 열린다 — 첫 하향 확장이 곧 동굴 진입이고, 이때
  자갈 생성기를 얻는다.

플레이어가 매 확장에서 "넓힐까 / 파고들까"를 고르므로, 진행 경로가 갈린다.
테마 하나 안에서 선택지가 생기는 게 지대를 나눈 이유다.

### 3.1 나무 체인 (숲)

| 레벨 | 이름 |
|---|---|
| 1 | 씨앗 |
| 2 | 새싹 |
| 3 | 묘목 |
| 4 | 나무 |
| 5 | **거목** → 목재 산출원 |

### 3.2 돌 체인 (동굴)

| 레벨 | 이름 |
|---|---|
| 1 | 자갈 |
| 2 | 돌멩이 |
| 3 | 바위 |
| 4 | 암반 |
| 5 | **광석바위** → 광석 산출원 |

### 3.3 체인 길이

첫 테마는 **5레벨**로 짧게 둔다. 프로토타입과 같은 길이라, 플레이어가 한 체인을
끝까지 보는 경험을 이르게 겪는다. 이후 테마는 길어져도 된다 — 체인 길이는
`ItemChain.maxLevel` 값 하나라 테마별로 다르게 잡는 비용이 없다.

## 4. 자원 산출 — 최고 레벨의 변신 **[제안 — 확인 필요]**

**최고 레벨 조각은 소멸하지 않고 자원 산출원이 된다.** 거목을 탭하면 목재가
창고에 들어가고, 거목은 그 칸에 남는다.

이 선택의 결과:

- 산출원이 칸을 영구 점유하므로 보드가 좁아진다 → 확장 동기(§2).
- "다 키운 것을 없애는" 상실감이 없다. 정원이 자라는 느낌이 남는다.
- 산출원이 여러 개면 산출량이 늘어난다 → 넓힐 이유가 명확하다.

대안(최고 레벨을 소모해 자원을 얻고 칸을 비움)은 반복을 강제하지만 진행감이
남지 않고, 보드 확장이 보상 축일 때 공간 압박이 사라져 루프가 헐거워진다.

**방치 산출 [제안]**: 탭 없이도 시간에 따라 산출원이 자원을 쌓아두게 한다.
이유 둘 — (1) 테마가 늘면 이전 테마 보드를 손으로 굴리는 노가다가 생기는데,
방치 산출이 그걸 없앤다. (2) 산출 가속·창고 확장이 수익 모델의 자리가 되어
PRD 수익모델 절이 억지 없이 채워진다.

## 5. 확장 비용 곡선 **[제안 — 초기값, 확정은 코드]**

아래 수치는 **모양을 합의하기 위한 첫 값**이다. 최종 숫자는 코드(또는 테마
데이터 파일)가 단일 출처이고, 이 문서는 의도만 남긴다.

| 단계 | 보드 | 비용 | 해금 |
|---|---|---|---|
| 시작 | 숲 3×4 (12칸) | — | 씨앗 생성기, 씨앗 2개 |
| 확장 1 | 숲 4×4 | 목재 5 | — |
| 확장 2 | 숲 4×5 | 목재 12 | — |
| **동굴 진입** | + 동굴 4×2 | 목재 25 | **자갈 생성기** |
| 확장 3 | 숲 5×5 / 동굴 5×2 | 목재 20 + 광석 8 | — |
| 확장 4 | 숲 5×6 / 동굴 5×3 | 목재 40 + 광석 20 | — |
| 테마 완주 | — | 목재 80 + 광석 50 | **다음 테마** |

의도:

- **첫 확장은 싸게.** 시작 보드 12칸은 씨앗 생성기 + 자라는 나무 몇 개로 금방
  찬다. 첫 확장이 몇 분 안에 오게 해서 루프를 즉시 학습시킨다.
- **동굴 진입 전까지는 목재만 요구한다.** 자원이 하나뿐인 동안 배울 게 적다.
- **동굴 이후는 두 자원을 함께 요구한다.** 한쪽만 파면 막히므로 두 지대를
  번갈아 돌보게 된다 — 지대를 나눈 설계가 여기서 기능한다.
- **다음 테마 해금이 이 테마의 마지막 목표다.** 테마 해금이 주 컨텐츠라는
  정체성이 진행 끝에 드러난다.

## 6. 다음 테마로 넘기는 것 (첫 테마 범위 밖)

첫 테마를 배우기 쉽게 두기 위해 의도적으로 넣지 않는다.

- **2차 가공** — 목재+광석으로 도구를 만드는 식. **보드 위 머지로 하지 않는다.**
  서로 다른 조각이 합쳐지기 시작하면 프로토타입에서 검증한 예측 가능성
  (조건 불일치 = 무조건 자리 교체)이 무너진다. 대신 **제작대를 생성기의 한 종류로**
  두고, 탭하면 창고 재료를 써서 결과물을 보드에 내놓게 한다. 머지 규칙은 불변.
- **세 번째 체인** — 물/이끼 등. 첫 테마는 2체인으로 충분한지 플레이로 본다.
- 도감, 장식/꾸미기, 주문·손님 요청, 사운드, 튜토리얼.

## 7. 결정 기록 (2026-11-05)

열려 있던 결정 6개 중 5개를 정했다. 수치(확률·보너스 배율·창고 용량)는 §5처럼
코드나 테마 데이터 파일이 단일 출처이고, 여기에는 규칙의 모양만 남긴다.

1. **확장 단위 [확정] — 행/열 통째.** UI가 단순하고 매 확장이 "넓히기 / 파고들기"
   중 하나를 고르는 선택으로 선명하게 남는다. §5 비용표를 그대로 쓴다.
   (기각: 칸 하나씩 — 매번 어느 칸을 열지 골라야 해서 번잡하다.)
2. **생성기 배치 [확정] — 자유 배치, 보너스로 유도.** 생성기와 조각은 어느 지대
   칸에든 놓을 수 있다. 드롭 판정(머지/이동/자리 교체/스냅백)에 예외를 만들지 않는다.
   지대의 의미는 6번의 보너스가 만든다.
   (기각: 자기 지대에만 — 드롭 판정에 "지대 불일치 = 스냅백" 예외가 생긴다.)
3. **생성기 머지 [확정] — 유지하되 효과는 확률로.** 같은 체인·같은 레벨 생성기끼리
   머지해 레벨을 올리는 것은 그대로 둔다(검증된 손맛). 다만 "생성기 레벨 = 스폰
   아이템 레벨"을 버리고, **생성기 레벨이 오를수록 상위 레벨 아이템이 나올 확률이
   오른다.** G1은 언제나 1레벨을 낸다. 상위 아이템으로 바로 가는 우회로를 줄이고
   하위 레벨 머지 구간을 살리기 위해서다. 레벨별 확률표는 데이터로 둔다.
4. **방치 산출 상한 [확정] — 창고 용량에서 멈춘다.** 창고가 가득 차면 방치 산출이
   멈춘다. 창고 확장이 진행 목표이자 수익 지점이 된다(§4).
   (기각: 오프라인 시간 상한 / 상한 없음 / 방치 산출 없음.)
5. **테마 총 개수와 다음 테마 정체 [보류]** — 첫 테마를 플레이한 뒤 정한다.
6. **지형 [확정] — 보너스만.** §1의 "생성기 1개 = 체인 1개"를 유지한다. 지형(지대)은
   스폰 종류를 정하지 않고, **산출원이 자기 체인과 맞는 지대 칸에 있으면 산출량이
   늘어난다** (거목이 숲에, 광석바위가 동굴에). 조작 규칙은 한 글자도 바뀌지 않는다.
   - 보너스 대상은 산출원만이다. 생성기 스폰 확률에는 지형 보너스를 주지 않는다 —
     확률을 움직이는 손잡이는 3번(생성기 레벨) 하나로 둔다.
   - **기각한 안과 이유** (2026-09-27 논의 요약):
     - 랜덤 칸 스폰 + 지형이 종류 결정 — 플레이어가 고를 손잡이가 없고, 체인이
       늘수록 짝 없는 외톨이가 쌓인다.
     - 플레이어가 칸을 골라 스폰 — 매 탭이 생산 계획이 되고 확장·지대·해금이 한
       메커닉으로 합쳐지는 장점이 있었지만, 탭당 조작이 하나 늘고 검증되지 않았다.
       첫 테마는 검증된 조작 그대로 간다. 다음 테마에서 다시 꺼낼 수 있는 안으로 남긴다.
     - 지형이 레벨·품질만 결정 — 3번의 확률 규칙과 역할이 겹친다.

## 8. 코드 영향 (이식 시점에 반영)

프로토타입 도메인은 대부분 그대로 쓰지만, 이 설계가 요구하는 변경이 있다.
`apps/proto_merge`는 고치지 않는다 — 새 앱으로 이식할 때 반영한다.

| 필요한 것 | 현재 | 변경 방향 |
|---|---|---|
| 보드 확장 | `columns`/`rows` 고정, `isInside`가 경계만 검사 | 칸별 해금 상태. `isInside` → `isUnlocked` |
| 지대 | 없음 | 칸마다 지대 속성 (숲/동굴). 배치 제약 없음 — 산출원의 산출량 보너스에만 쓴다 (§7-2·6) |
| 자원 창고 | 없음 | 보드 밖 상태 = **아웃게임**이므로 Riverpod 담당 (`docs/03-architecture.md` §3) |
| 자원 산출원 | `Generator`는 아이템을 **보드에** 스폰 | 자원을 **창고로** 내는 종류를 분리. `CellContent` 하위 타입 추가 |
| 최고 레벨 변신 | 최고 레벨은 머지만 막힘 | 최고 레벨 도달 시 산출원으로 전환 |
| 생성기 스폰 | `Generator.produce()`가 `min(level, maxLevel)` 고정 | 생성기 레벨별 확률표로 아이템 레벨을 뽑는다. G1은 1레벨 고정 (§7-3) |
| 창고 상한 | 없음 | 자원별 용량. 가득 차면 방치 산출 정지 (§7-4) |
| 테마 정의 | `ItemChain` 상수 | 테마 = 체인 묶음 + 해금 조건 + 확장 비용, **데이터로 정의** |

마지막 줄이 중요하다. 테마를 데이터로 정의해두면 테마 추가가 코드 수정이 아니라
데이터 추가가 되고, 그게 이 게임의 컨텐츠 확장 방식이 된다.

그래픽은 이미 분리돼 있다 — `lib/game/skins/`의 레지스트리 한 곳만 고치면
보드 전체 그림이 교체되고, 머지 결과는 레벨이 오른 새 조각으로 컴포넌트를
다시 만들기 때문에 "머지 → 다음 레벨 그림"이 자동으로 따라온다.
