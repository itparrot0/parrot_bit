# 패키지 경계 정의

> 각 패키지가 **무엇을 포함하고, 무엇을 절대 포함하지 않는지** 정의한다.
> "이 코드 어디에 두지?"의 답이 이 문서에서 30초 안에 나와야 한다.
> 의존 방향 규칙은 `docs/03-architecture.md` §5를 따른다.

## 공통 규칙

- 모든 패키지는 배럴 파일 하나(`lib/<package_name>.dart`)만 공개 API로 노출한다. `src/` 내부 파일 직접 import 금지.
- 패키지는 **도메인(비즈니스 개념)을 모른다.** "점수", "유저", "상품" 같은 타입이 `core_*`에 등장하면 잘못 들어온 것이다.
- 패키지는 앱 없이 단독 테스트 가능해야 한다.
- 외부 SDK(firebase, dio 등) 타입을 공개 API에 노출하지 않는다 — 교체 가능성을 위해 자체 타입으로 감싼다.

---

## core_utils — 순수 유틸

- **한 문장**: Flutter에 의존하지 않는 순수 Dart 함수/확장.
- **포함**: 날짜/문자열/숫자 포맷, 컬렉션 확장, Result 타입 등 공용 헬퍼, 상수.
- **금지**: Flutter import (`dart:ui` 포함), I/O, 상태. `flutter:` 의존이 pubspec에 생기면 위반.
- **의존**: 없음 (모든 패키지의 최하층).

## core_ui — 공통 위젯, 테마, 디자인 토큰

- **한 문장**: 모든 앱이 공유하는 시각 언어(토큰·테마·범용 위젯).
- **포함**: 색/타이포/간격 디자인 토큰, ThemeData 빌더, 앱 로직 없는 범용 위젯(버튼, 로딩, 빈 화면, 에러 뷰), 공용 아이콘/폰트 에셋.
- **금지**: 화면(Screen/Page) 단위 위젯, 라우팅, 상태관리 Provider, 네트워크/저장소 접근, Flame 관련 코드. "특정 앱에서만 쓰는 위젯"은 그 앱의 `lib/widgets/`에 둔다.
- **의존**: core_utils.

## core_network — API 클라이언트, 에러 처리

- **한 문장**: HTTP 통신과 그 실패를 정규화하는 계층.
- **포함**: 설정된 HTTP 클라이언트 팩토리(base url·타임아웃·재시도·로깅 인터셉터), 정규화된 예외 체계(`NetworkException` 등: 타임아웃/오프라인/4xx/5xx 구분), 공통 응답 언랩 헬퍼.
- **금지**: 특정 API 엔드포인트 정의, 응답 도메인 모델, 캐싱 정책(그건 앱 Repository 몫), 토큰 저장(core_storage를 앱에서 조합).
- **의존**: core_utils. (dio는 내부 구현 — 공개 API에 dio 타입 노출 금지)

## core_storage — 로컬 저장소 추상화

- **한 문장**: key-value 및 구조화 로컬 저장의 추상 인터페이스와 구현.
- **포함**: `KeyValueStore` 등 추상 인터페이스, shared_preferences/(필요 시 drift) 기반 구현체, 마이그레이션 헬퍼, 저장 실패 예외 체계.
- **금지**: "무엇을" 저장할지에 대한 지식(키 이름·스키마는 앱이 정의), 원격 동기화, 보안 자격증명 로직(필요해지면 별도 `core_secure_storage` 검토).
- **의존**: core_utils.

## core_analytics — 로깅/분석

- **한 문장**: 이벤트 로깅의 추상 인터페이스와 벤더 구현.
- **포함**: `Analytics` 인터페이스(`logEvent(name, params)`, 화면 추적), 콘솔(디버그)/실서비스(예: Firebase) 구현체, 앱 로그용 `Logger`.
- **금지**: 이벤트 이름·파라미터 정의(이벤트 카탈로그는 각 앱 소유), 크래시 리포팅 초기화 같은 앱 부트스트랩 로직.
- **의존**: core_utils.
- **주입 방식**: 인터페이스만 패키지에 두고, 어떤 구현을 쓸지는 각 앱의 main()에서 결정한다 (프로토타입 앱은 콘솔 구현으로 충분).

## core_game — Flame 공통 컴포넌트 (지금은 만들지 않음)

- **생성 조건**: 게임 앱이 **2개째** 생기고 실제로 공유할 Flame 코드가 확인된 시점 (Rule of Two). 첫 게임 개발 중에는 후보 코드를 게임 앱 내부에 둔다.
- **포함(예상)**: 공용 Flame 컴포넌트(조이스틱, 카메라 셰이크, 파티클 프리셋), 게임 루프 유틸, 오디오 래퍼.
- **금지**: 특정 게임의 규칙/밸런스/엔티티.
- **의존**: core_utils, flame.

## 판단이 애매할 때

| 상황 | 답 |
|------|-----|
| 한 앱에서만 쓰는 코드 | 그 앱 `lib/` 내부. 두 번째 사용처가 생길 때 추출 |
| 터치/드래그 등 기본 입력 처리 | 저수준 입력 래핑 패키지(`core_input` 류)는 만들지 않는다 — Flutter(`GestureDetector` 등)와 Flame(`TapCallbacks` 등)이 이미 그 공통 계층이고, 둘은 좌표계·이벤트 모델이 달라 통합 추상화가 불가능하다. 추출 대상은 기본 동작을 조합한 **완성된 인터랙션 컴포넌트**뿐: 위젯이면 `core_ui`, Flame 컴포넌트면 `core_game`, 터치 타깃 크기·햅틱 정책 같은 상수는 `core_ui` 토큰. 시점은 Rule of Two |
| 도메인 개념이 들어간 공용 코드 | `core_*` 금지. 필요 시 `feature_<도메인>` 패키지 신설 검토 |
| 프로토타입에서 패키지 수정이 필요 | 패키지를 고치지 말고 앱 로컬에 복사해 실험, 승격 시 정식 반영 |
| 패키지 A가 패키지 B의 기능이 필요 (core_utils 제외) | 패키지에서 조합하지 말고 앱에서 조합 |
