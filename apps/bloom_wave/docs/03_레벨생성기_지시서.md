# 03. 레벨 생성기 지시서 — 픽셀 아트에서 "항상 클리어 가능한" 레벨 만들기

> **기록용 (2026-11-04 Flutter 전환 이전 기준).** 이 문서의 TypeScript·npm·Capacitor 세부는 지금 코드와 다릅니다. 현재 구조는 [../README.md](../README.md)를 보세요.

## 목표
디자이너가 그린 픽셀 아트 PNG를 넣으면, **솔버로 클리어 가능이 검증된** 레벨 JSON을 원하는 난이도로 대량 생성하는 Node CLI를 만듭니다.

## 입력
- `reference/src/generator.ts`, `solver.ts`, `engine.ts` (핵심 알고리즘은 이미 구현·테스트됨)
- 픽셀 아트 PNG (권장 8×8 ~ 16×16, 투명 배경, 6색 이하)
- `01_게임기획서.md` 7장 난이도 곡선, 10장 데이터 형식

## 산출물
- `tools/levelgen/` CLI
  - `levelgen build levels.config.json` → `out/pack-01.json`, `out/report.csv`, `out/previews/*.png`
  - `levelgen verify out/pack-01.json` → 모든 레벨을 솔버로 다시 검증 (CI용)
- 출시용 레벨 120개가 든 `pack-01.json`

## 생성 알고리즘 (참조 구현과 동일)

```
1. PNG → 칸 배열
   알파 < 128 → 빈 칸, 나머지는 팔레트 색 인덱스

2. 시작 발아 지점
   8방향으로 이어진 덩어리마다 1개를 무작위로 고르고, 부족하면 starts 개수까지 추가
   (전염이 8방향이므로 덩어리마다 하나는 반드시 있어야 함)

3. 구성적 대기열 — "실제로 두어 보며 기록"
   반복 (안 핀 칸이 남아 있는 동안, 슬롯은 항상 빈 안정 상태):
       발아 칸이 있는 색 중 하나를 무작위로 고름
       그 색 물방울을 무한한 양으로 혼자 넣었을 때 안정될 때까지 피는 칸 수 = max
       양 = min(max, rand(dropMin..dropMax))
       그 물방울을 넣고 안정될 때까지 진행, (색, 양)을 대기열에 추가
   → 양이 max 이하라 매번 다 쓰이고 슬롯이 비므로, 이 순서는 무조건 클리어. 물방울 총량 = 칸 수

4. 난이도 올리기 — 언덕 오르기
   반복 (시도 횟수 남음 && 목표 미달):
       대기열에서 물방울 하나를 골라 더 앞쪽 위치로 옮김
       클리어 가능한지 확인
         - 확정 규칙(웨이브 중 탭 허용): 솔버로 "넣기/기다리기" 수순을 탐색, 노드 한도 초과면 버림
         - 비교용 TURN_BASED(웨이브 후에만 탭): 수순이 하나뿐이므로 끝까지 시뮬레이션
       목표값 = (1 - 무작위 클리어율)×100 + 슬롯 최대 점유×10 + 평균 점유
       목표값이 떨어지면 버리고, 아니면 채택
   목표: 슬롯 최대 점유 ≥ targetPeak(기본 3) 그리고 무작위 클리어율 ≤ targetWinRate

5. 최종 지표: 슬롯 최대/평균 점유, 무작위 봇 300판 클리어율, 솔버 노드 수, score(0~100)
```

**왜 이렇게 하나요?** 무작위 대기열을 만든 뒤 풀리는지 검사하면 대부분 풀리지 않아 시간이 낭비됩니다. 구성적으로 만들면 출발점이 항상 풀리는 레벨이고, 이후의 모든 변경은 다시 검증합니다. 그래서 **결과물은 언제나 클리어 가능**합니다.

### 참조 구현으로 측정한 결과 (확정 규칙, 물방울 양 1~4, 시드 4개)
무작위로 "넣기/기다리기"를 고르는 봇의 클리어율과 레벨 하나당 생성 시간입니다.

| 그림 | 순서 흔들기 150회 | 1500회 | 1500회 생성 시간 |
|---|---|---|---|
| tulip (31칸) | 100% | 100% | 3~4s |
| mushroom (66칸) | 11~100% | 7~73% | 0.1~7s |
| sunflower (81칸) | 13~100% | 10~100% | 0.5~10s |

- 작은 그림(30칸 안팎, 3색 이하)은 어렵게 만들 수 없습니다. 튜토리얼에 씁니다.
- 시드에 따라 쉬운 배치에 갇히는 경우가 있어 결과가 둘로 갈립니다. **그림마다 시드를 5~10개 돌려 목표에 가장 가까운 것을 고르는 것**이 순서 흔들기 횟수를 늘리는 것보다 효율적입니다.
- 목표에 도달하면 바로 멈추므로, 쉽게 어려워지는 시드는 1초 안에 끝납니다.
- 비교용 규칙(`TURN_BASED`, `queuePick` 2~3)의 측정값은 `node reference/src/sweep.ts`로 다시 볼 수 있습니다.

## 작업 단계
1. **CLI 골격**: `tools/levelgen/`에 `reference/src`의 엔진·솔버·생성기를 복사하거나 공유 패키지(`packages/core`)로 분리합니다. **권장은 공유 패키지**입니다. 앱과 생성기가 같은 규칙 코드를 쓰게 되어 규칙 불일치 버그를 원천적으로 막습니다.
2. **PNG 입력**: `pngjs`로 읽습니다.
   - 알파 < 128 → 빈 칸
   - 같은 RGB는 같은 색. 색이 `maxColors`보다 많으면 가장 가까운 색끼리 합칩니다(RGB 거리 기준 병합).
   - 3칸 미만인 색은 이웃 색으로 합칠지 경고합니다. 너무 작은 색은 답답한 레벨을 만듭니다.
   - 크기가 16×16을 넘으면 경고합니다. 모바일에서 칸이 너무 작아집니다.
3. **설정 파일** `levels.config.json`:
   ```json
   {
     "pack": "pack-01",
     "defaults": { "slotCount": 4, "options": { "queuePick": 1, "realtime": true }, "displacements": 1500, "maxSolverNodes": 50000 },
     "levels": [
       { "art": "art/tulip.png",    "seeds": [1,2,3], "starts": 2, "dropMin": 3, "dropMax": 6, "targetWinRate": 1.0 },
       { "art": "art/mushroom.png", "seeds": [1,2,3,4,5], "starts": 1, "dropMin": 1, "dropMax": 3, "targetWinRate": 0.2 }
     ]
   }
   ```
   - 그림 하나에 시드 여러 개를 돌리고, 목표 난이도 구간에 가장 가까운 결과를 고릅니다.
4. **병렬 처리**: 레벨마다 `worker_threads`로 나눕니다. 120레벨 × 시드 5개 기준 몇 분 안에 끝나야 합니다.
5. **정렬과 배치**: score 기준으로 정렬한 뒤 `01_게임기획서.md` 7.3의 구간에 배치합니다. 10레벨마다 쉬운 레벨을 하나 끼워 넣습니다.
6. **별점 기준**: 솔버를 "슬롯 최대 점유 최소화" 목적으로 한 번 더 돌려 ★3 기준값을 `meta`에 넣습니다. 노드 한도를 넘으면 생성 수순의 값을 씁니다.
7. **리포트**: `report.csv` (id, 색상 수, 칸 수, 물방울 수, 슬롯 최대/평균 점유, 클리어율, 노드 수, score)와 미리보기 PNG(시작 상태: 씨앗/발아 표시)를 만듭니다.
8. **verify 명령**: 팩의 모든 레벨에 대해 ①물방울 총량 = 칸 수 ②8방향 덩어리마다 시작 지점 존재 ③솔버 클리어 가능 ④해법 재생 시 클리어를 검사합니다. 하나라도 실패하면 종료 코드 1로 끝냅니다.
9. **결정성**: 같은 설정과 시드면 같은 결과가 나와야 합니다(`mulberry32` 시드 RNG만 사용, `Math.random` 금지).

## 큰 그림(16×16 이상)에서 솔버가 느릴 때
- 지금은 상태 키가 문자열입니다. **Zobrist 해시**(칸 상태별 64비트 난수 XOR)로 바꾸면 메모리와 속도가 크게 좋아집니다.
- 실시간 규칙의 분기는 "넣기/기다리기" 두 개뿐이지만 수순이 길어집니다. 한 번에 여러 틱을 기다리는 수("k틱 뒤 넣기")로 묶고, 슬롯이 이미 찬 동안은 기다리기만 남으므로 그 구간을 건너뛰면 탐색이 짧아집니다.
- `solvable: null`(노드 한도 초과)이 나온 후보는 **채택하지 않습니다**. 클리어 가능 보장이 깨지지 않게 하기 위해서입니다.

## 완료 기준
- [ ] `levelgen build` 한 번으로 120레벨 팩과 리포트 생성
- [ ] `levelgen verify` 통과 (CI에서 매번 실행)
- [ ] 리포트의 score가 레벨 번호를 따라 대체로 올라감 (구간별 목표 클리어율 충족)
- [ ] 같은 설정을 두 번 돌리면 결과 파일이 바이트 단위로 같음
